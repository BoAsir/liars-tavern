# 骗子酒馆(Liar's Tavern)设计文档

- 日期:2026-08-14
- 状态:已确认
- 平台:桌面客户端(Windows / macOS),Godot 4.3+,GDScript,中文 UI
- 联机:局域网 2–4 人,纯真人对战

## 1. 概述

《骗子酒馆》是一款局域网多人吹牛出牌游戏。玩家轮流盖牌打出并声称是本局目标牌,
下家可以质疑;质疑判定后输的一方对自己进行一次俄罗斯轮盘射击,最后存活者获胜。

首版范围:仅"骗子牌"模式、2–4 名真人玩家、2D 牌桌视角、局域网自动发现 + 手输 IP 兜底。
明确不做:AI 补位、骗子骰模式、3D 场景、互联网联机、断线重连(游戏中断线即淘汰)。

## 2. 游戏规则(骗子牌)

### 2.1 牌堆与发牌

- 牌堆共 20 张:Q×6、K×6、A×6、鬼牌×2(鬼牌为万能牌,视同任意目标牌)。
- 每小局开始:随机抽定目标牌型(Q / K / A 之一),每名存活玩家发 5 张手牌,余牌弃置不用。
- 首小局随机确定起始玩家;之后每小局由上一小局开枪者(若存活,否则其下家)先手。
- 行动顺序按座位顺时针轮转,跳过已淘汰玩家和本小局手牌已空的玩家。

### 2.2 回合行动

轮到某玩家时,二选一:

1. **出牌**:盖着打出 1–3 张手牌,声称"这些全部是目标牌"(允许说谎)。
2. **质疑**:翻开上家刚打出的那组牌进行验证。本小局第一个行动者只能出牌(没有可质疑对象)。

回合限时 30 秒:超时由房主端代为打出手牌中最靠前的 1 张(最少合法出牌),防止挂机卡死全场。

### 2.3 质疑判定

- 翻开的牌**全部**是目标牌或鬼牌 → 质疑失败,**质疑者**开枪。
- 只要有一张不是 → 说谎坐实,**出牌者**开枪。

### 2.4 左轮手枪(俄罗斯轮盘)

- 每名玩家一把 6 膛左轮,整局(match)开始时装 1 发子弹于随机膛位(1–6 均匀随机)。
- 每次开枪扣一次扳机;空枪后弹巢前进一格,同一玩家下次开枪命中概率递增,第 6 次必中。
- 中弹 → 立即淘汰(整局内不再参与)。
- 每次开枪(无论结果)结束当前小局:重抽目标牌、重新发牌,进入新小局。

### 2.5 手牌打空与强制验证

- 手牌打空的玩家本小局内被轮转跳过,处于安全旁观状态。
- 若场上仅剩一名存活玩家手中有牌,该玩家必须出牌,且系统自动翻牌验证(等效被强制质疑),按 2.3 判定。

### 2.6 胜负与再来一局

- 最后存活者获胜。结算画面展示胜者与各玩家存活轮数。
- 结束后所有人回到等待厅,可直接再开一局(重置左轮与牌堆)。

## 3. 总体架构

### 3.1 权威模型

- **房主权威(listen server)**:房主进程同时是服务端与玩家。全部规则逻辑(`src/core/`)只在房主端执行。
- 客户端只发送**意图**(出牌 / 质疑 / 准备),房主校验合法性后推进状态机,再向每个玩家定向下发其**可见视图**。
- 手牌、弹膛位置等秘密信息永不发送给无权查看的客户端,从协议层面杜绝作弊。

### 3.2 分层与目录结构

纯逻辑与表现分离:`core/` 不依赖节点树、网络与 UI,可被 GUT 直接单测。

```text
LiarsTavern/
├── project.godot
├── src/
│   ├── core/                  # 纯游戏逻辑(无网络、无UI)
│   │   ├── game_state.gd      # 状态机:发牌→轮转→质疑→开枪→结算
│   │   ├── deck.gd            # 牌堆构建/洗牌/发牌
│   │   ├── revolver.gd        # 弹膛模型
│   │   └── rules.gd           # 行动合法性校验、质疑判定
│   ├── net/
│   │   ├── network_manager.gd # ENet 建房/加入/RPC 路由(autoload)
│   │   ├── discovery.gd       # UDP 广播房间发现
│   │   └── protocol.gd        # 消息常量与载荷结构
│   └── ui/
│       ├── main_menu/         # 主菜单(昵称/建房/房间列表/输IP)
│       ├── lobby/             # 等待厅(玩家列表/准备/开始/踢人)
│       └── table/             # 牌桌主场景(手牌/出牌/质疑/开枪演出)
├── assets/                    # 卡面、桌布、左轮、音效、字体
└── tests/                     # GUT 单元测试
```

## 4. 网络设计

### 4.1 房间发现(双通道)

- 房主每 1 秒向局域网 UDP 广播(端口 `47800`)房间信息:房名、房主昵称、当前人数/上限、协议版本号、游戏端口。
- 客户端主菜单监听广播,实时刷新房间列表,点击加入。
- 兜底:房间列表下方常驻"输入 IP 直连"入口。
- 协议版本号不匹配时拒绝加入并提示升级。

### 4.2 游戏通信(ENet,端口 `47801`)

客户端 → 房主(意图):

| 消息 | 载荷 | 说明 |
|---|---|---|
| `intent_play` | 手牌下标数组(1–3 个) | 请求出牌 |
| `intent_challenge` | 无 | 请求质疑上家 |
| `lobby_ready` | bool | 等待厅准备/取消 |

房主 → 客户端(视图与事件):

| 消息 | 范围 | 内容 |
|---|---|---|
| `state_public` | 广播 | 目标牌、当前行动者、各玩家手牌张数、上家声称数量、存活状态、各玩家已扣扳机次数、小局/整局阶段。每次状态变更全量推送。 |
| `state_private` | 定向 | 仅本人手牌 |
| `event_reveal` | 广播 | 质疑翻牌结果(此时才公开这组牌) |
| `event_gunshot` | 广播 | 开枪者、是否中弹(弹膛位置永不下发) |
| `intent_rejected` | 定向 | 错误码(非你回合 / 下标越界 / 张数非法等) |

- 非法意图房主直接拒绝;客户端 UI 同时做前置禁用(按钮置灰),双重防护。
- 状态量小,采用全量推送,避免增量同步的一致性问题。

## 5. 界面流程与牌桌演出

```text
主菜单 ──建房──▶ 等待厅(房主) ──全员准备+开始──▶ 牌桌 ──▶ 结算 ──▶ 等待厅
   │                                              ▲
   └─选房间/输IP──▶ 等待厅(客) ────────────────────┘
```

- **主菜单**:昵称输入(本地持久化)、创建房间、自动发现的房间列表、手输 IP 直连。
- **等待厅**:玩家列表与准备状态;房主可踢人;2–4 人且全员准备后房主可开始。
- **牌桌**(2D 斜视角酒馆圆桌):
  - 自己手牌扇形展开于底部,点选 1–3 张后"出牌"按钮亮起;轮到自己且非首行动者时"质疑"按钮可用。
  - 其他玩家沿桌边分布:头像、牌背数量、存活状态、已扣扳机次数。
  - 桌面中央:目标牌大图标、上家盖牌堆、声称数量气泡、回合倒计时。
  - **演出序列**(房主事件驱动,期间锁输入,约 3–5 秒):质疑翻牌逐张揭示 → 聚焦开枪者 → 举枪/转轮音效/扣扳机 → 空枪(咔哒)或中弹(枪声 + 震屏 + 头像变灰)。

## 6. 容错与错误处理

- 游戏中玩家断线 → 立即淘汰并广播提示,游戏继续;若仅剩 1 名存活者则其直接获胜。
- 房主断线 → 房间解散,所有客户端弹窗提示并返回主菜单(listen-server 固有限制,首版接受)。
- 等待厅断线 → 移出玩家列表并广播更新。
- 所有网络回调经统一错误出口处理,UI 始终给出明确提示,不静默失败。
- 加入房间的边界:房间已满 / 游戏已开始 / 版本不匹配,均返回明确错误码并在客户端提示。

## 7. 测试策略

- **单元测试(GUT)**:覆盖 `src/core/` 全部逻辑,目标覆盖率 80%+:
  - 牌堆构成与发牌数量;
  - 质疑判定真值表(含鬼牌、混合牌组边界);
  - 弹膛模型:随机装弹分布、空枪推进、第 6 次必中;
  - 状态机全路径:轮转跳过(淘汰者/空手者)、强制验证、超时代打、小局/整局切换、胜负判定。
- **联机手动验收**:
  - 单机开 2–4 个实例走完整局;
  - 两台真实机器验证:UDP 自动发现、手输 IP 直连、游戏中断线淘汰、房主断线解散。
- 架构上 core 与节点分离,CI 可用 headless Godot 运行 GUT。

## 8. 里程碑建议

1. **M1 核心逻辑**:core 状态机 + 全部单测通过(无 UI、无网络)。
2. **M2 单机走查**:本地单进程模拟 4 座位跑通整局(调试 UI)。
3. **M3 联机**:ENet 接入、意图/视图协议、多实例联机对局。
4. **M4 发现与大厅**:UDP 房间发现、手输 IP、等待厅完整流程。
5. **M5 演出与打磨**:牌桌美术、翻牌/开枪演出、音效、结算、容错完善。
